1. מה הפיצ'ר עושה (מבט משתמש)

בטבלת הפריטים (המסך הראשי שמציג את כל הפריטים שנקלטו) נוספה עמודה בשם "פעולות" ובה כפתור עיפרון ✏️. לחיצה עליו פותחת חלון בשם "עריכת פריט #מספר". בחלון הזה אפשר:

✏️ לערוך את פרטי הפריט

לקוח, סוג פריט, מספר סיריאלי, מק"ט, דגם, יצרן ומספר יצרן.

ברקוד, סטטוס והתקדמות מוצגים לקריאה בלבד. אי אפשר לשנות אותם מכאן, כי תהליך הבדיקה בתחנות הוא שקובע אותם.

🗑️ למחוק את הפריט

כפתור אדום "מחק פריט" בתחתית החלון. לפני המחיקה נפתח חלון אישור נוסף.

אם לפריט יש פריטים שתלויים בו (פריטים מחוברים, או פריטים בתוך מארז), המערכת מציגה את רשימתם ומבקשת אישור למחוק את כולם יחד.

2. מושגי יסוד במערכת

כדי להבין את הקוד צריך להכיר כמה טבלאות ומושגים. זה החלק החשוב ביותר, כי רוב המורכבות של הפיצ'ר נובעת מהם.

הטבלאות "התפעוליות"

טבלהמה היא שומרת
itemsהפריט עצמו: לקוח, סוג, סיריאלי, מק"ט, דגם, יצרן, משלוח. זה "כרטיס הזהות" של הפריט.
item_routesאיפה הפריט נמצא כרגע במסלול הבדיקות: באיזה שלב (current_route_step), מה הסטטוס (current_status: 1 בבדיקה, 2 בתור, 3 הושלם), באיזו תחנה, ואם הוא סיים. שורה אחת לכל פריט.
item_route_historyהיסטוריה: כל מעבר של הפריט בתחנה, מתי נכנס לתור, מתי התחיל ומתי סיים.
test_resultsתוצאות הבדיקות שנרשמו לפריט.
testing_routesהגדרת המסלולים: לכל סוג פריט רשימת שלבים (route_steps), למשל {5,7,6,8}, כלומר סוגי תחנות לפי הסדר.

לדג'ר המדדים (Metrics Ledger)

זו שכבה נפרדת שנבנתה כדי להזין את לוח הניהול (הדשבורד): כמה פריטים הושלמו, זמני טיפול, עומס בתחנות וכדומה. במקום לחשב את כל זה כל פעם מחדש מהטבלאות התפעוליות, המערכת רושמת כל אירוע ובונה ממנו טבלאות מוכנות לקריאה:

טבלהמה היא שומרת
route_run"ריצה": מעבר אחד של פריט על המסלול, מההתחלה ועד הסוף. ריצה שנסגרה (closed_at מלא) נחשבת פריט שהושלם. יש גם שדה is_trusted: ריצה לא-אמינה לא נספרת בדשבורד.
item_state_eventיומן אירועים: "הפריט נכנס לתור", "התחיל בדיקה" וכו'. הטבלה היא append-only, כלומר אפשר רק להוסיף שורות. טריגר בבסיס הנתונים חוסם עדכון או מחיקה.
item_state_intervalקטעי זמן: מתי הפריט היה בכל מצב ובכל תחנה, כולל זמן "קיר" וזמן עבודה נטו. קטע שעדיין פתוח = הפריט עדיין במצב הזה.
הנקודה הקריטית: אין מפתח זר (FK) מהלדג'ר ל-items כדי שהשאילתות של הדשבורד יהיו מהירות, הלדג'ר מעתיק ו"מקפיא" את פרטי הפריט (לקוח, משלוח, סיריאלי, סוג) לתוך כל ריצה וכל קטע זמן, כך שאף שאילתה לא צריכה לעשות JOIN לטבלת items. המחיר: בסיס הנתונים לא יודע שהשורות האלה שייכות לפריט. אם מוחקים פריט או משנים את הלקוח שלו, שום דבר לא נכשל, והנתונים בלדג'ר פשוט נשארים שגויים בשקט. זו בדיוק הבעיה ששלב 2 פותר.

מושגים טכניים

מושגהסבר
טרנזקציה (Transaction)קבוצת פעולות על בסיס הנתונים שמתבצעות "הכול או כלום". אם פעולה אחת נכשלת, כל השאר מבוטלות. בקוד: prisma.$transaction(async (tx) => {...}), וכל פעולה בתוכה משתמשת ב-tx.
FK (מפתח זר)קשר שבסיס הנתונים אוכף בין טבלאות. למשל items.parent_item_id מצביע על פריט אחר, ולכן אי אפשר למחוק פריט "אבא" כשיש לו "ילדים".
Prismaהספרייה שדרכה הקוד מדבר עם PostgreSQL. tx.items.update(...) = פקודת UPDATE.
API Routeבפרויקט Next.js, קובץ route.ts בתיקייה src/app/api/... מגדיר כתובת בשרת. פונקציה בשם PUT מטפלת בבקשות עדכון, ו-DELETE בבקשות מחיקה.
פונקציית DB (plpgsql)פונקציה שכתובה ב-SQL ויושבת בתוך PostgreSQL. היא נוצרת בקובץ migration ונקראת מהקוד עם SELECT function_name(...).

מחיקה בשני שלבים: handleDeleteConfirm

זה החלק המעניין. לחיצה על "מחק פריט" לא מוחקת מיד. היא פותחת חלון אישור שני שנערם מעל החלון הראשון (zIndex: 70 מול 60). בחלון הזה יש שני מצבים:

  1. מחיקה רגילה: נשלח DELETE בלי גוף.
  2. אם השרת עונה 409 עם רשימת connectedItems, זה לא נחשב כישלון. החלון עובר למצב שמציג את הפריטים המחוברים בשמם, עם כפתור "מחק את הפריט והפריטים המחוברים". לחיצה עליו שולחת שוב DELETE, הפעם עם { cascade: true }.
const handleDeleteConfirm = async (cascade = false) => {
  const res = await apiFetch(`/api/items/${item.item_id}`, {
    method: "DELETE",
    ...(cascade ? { headers: {...}, body: JSON.stringify({ cascade: true }) } : {}),
  });
  if (!res.ok) {
    const err = await res.json().catch(() => ({}));
    if (res.status === 409 && Array.isArray(err.connectedItems)) {
      setConnectedItems(err.connectedItems);   // מציגים את הרשימה ומחכים להחלטה
      return;
    }
    throw new Error(err.error || "מחיקת הפריט נכשלה");
  }
  onDeleted(true);
  onClose();
};
למה ככה ולא לשאול מראש?הלקוח (הדפדפן) לא יודע אם לפריט יש פריטים מחוברים. במקום בקשה נפרדת כדי לבדוק, השרת בודק בעצמו ומחזיר את הרשימה אם צריך. כך יש רק מקור אמת אחד, ואי אפשר למחוק "בטעות" גם את הילדים בלי שהמשתמש ראה אותם.

גם הטקסט של האישור משתנה לפי מצב הפריט: אם הפריט כבר עבר שלב בבדיקות (hasProgress), מוצגת אזהרה חזקה יותר, שגם היסטוריית הבדיקות ותוצאותיו יימחקו לצמיתות.

רכיבי עזר

בתחתית הקובץ יש שלוש קומפוננטות קטנות: Field (תווית + שדה), ReadOnlyPill (ה"כמוסות" של ברקוד/סטטוס/התקדמות), ו-Select, עטיפה של SearchableCombobox שממירה בין מחרוזת לאובייקט אפשרות.

5.4 השרת: PUT ו-DELETE

src/app/api/items/[id]/route.ts

לקובץ הזה כבר הייתה פונקציית GET (להצגת פריט). נוספו שתיים:

PUT בגרסה הראשונה

פשוט: קורא את הגוף, בודק שכל השדות מלאים (אחרת 400), ומעדכן את שורת הפריט ב-items. בגרסה הזו אפשר היה גם לשנות משלוח (shipment_id). אם הפריט לא קיים, Prisma זורקת שגיאה עם הקוד P2025, והשרת ממיר אותה ל-404.

const updated = await prisma.items.update({
  where: { item_id: itemIdBig },
  data: { customer_id: Number(customer), item_type_id: Number(itemType), ..., shipment_id: Number(shipment) },
});

DELETE בגרסה הראשונה

למה צריך למחוק ידנית ארבע טבלאות? כי ל-item_routes, item_route_history ו-test_results אין FK ל-items. אם מוחקים רק את הפריט, השורות שלהן נשארות "יתומות". לכן המחיקה עוברת על כולן, בסדר הזה, בתוך טרנזקציה:

await prisma.$transaction(async (tx) => {
  await tx.test_results.deleteMany({ where: { item_id: { in: idsToDelete } } });
  await tx.item_route_history.deleteMany(...);
  await tx.item_routes.deleteMany(...);
  // קודם הילדים: הם מחזיקים את ה-FK (parent_item_id) לאבא
  if (children.length > 0) await tx.items.deleteMany(...children);
  await tx.items.delete({ where: { item_id: itemIdBig } });
});

ולפני כל זה, הבדיקה של הילדים: אם יש כאלה ולא נשלח cascade: true, השרת מחזיר 409 עם הרשימה, כמו שתואר קודם.

6. שלב 2: חיבור ללדג'ר המדדים a75d79b

6.1 הבעיה

הפיצ'ר נכתב על main לפני שהלדג'ר מוזג, ולכן לא ידע עליו. ובגלל שלדג'ר בכוונה בלי FK, שום דבר לא נכשל. אבל שני המסלולים היו שגויים בשקט:

מחיקה השאירה "רוח רפאים"הפריט נמחק, אבל הריצה, האירועים וקטעי הזמן שלו נשארו בלדג'ר. קטע הזמן הפתוח נשאר פתוח לנצח, ולכן כל מספר בדשבורד המשיך לספור פריט שכבר לא קיים. בנוסף, בדיקת בריאות בשם runs_open_past_60d הייתה נדלקת באדום כעבור 60 יום, בלי שום דרך לדעת למה.
עריכה לא הגיעה לדשבורדנניח שמתקנים לקוח שהוקלד לא נכון. items מתעדכן, אבל העותקים ה"מוקפאים" בריצות ובקטעי הזמן נשארים עם הלקוח הישן, כך שבדשבורד הפריט המשיך להיות משויך ללקוח הקודם.

6.2 הפתרון: שלוש פונקציות בבסיס הנתונים

prisma/migrations/20260902000000_metrics_item_lifecycle/migration.sql

הפונקציות נכתבו ב-SQL, בתוך בסיס הנתונים, כי שם גם שאר הכללים (invariants) של הלדג'ר נאכפים. כך הכללים נשארים במקום אחד.

metrics_forget_item(item_id): "לשכוח" פריט

מוחקת את כל עקבות הפריט בלדג'ר. הסדר נכפה על ידי המפתחות הזרים שבתוך הלדג'ר עצמו:

  1. נעילה (pg_advisory_xact_lock) על הפריט, אותה נעילה שבה משתמשות פונקציות הלדג'ר האחרות, כדי שמחיקה לא תתנגש עם עדכון במקביל.
  2. מחיקת קטעי הזמן (item_state_interval), כי הם מצביעים גם על הריצה וגם על האירועים.
  3. ניתוק test_results.state_event_id מהאירועים שעומדים להימחק.
  4. פתיחת "פתח המילוט" (הסבר בהמשך) ומחיקת האירועים (item_state_event), ואז סגירתו מיד.
  5. מחיקת הריצות (route_run).
  6. מחיקה מטבלת metrics_drift, רק אם היא עדיין קיימת. בדיקה עם to_regclass, כי זו טבלה זמנית שנמחקת שבוע אחרי ההתקנה, ובלי הבדיקה הפונקציה הייתה מתחילה להיכשל ביום שהיא נמחקה.

הפונקציה אידמפוטנטית: הרצה שנייה לא עושה כלום ולא נכשלת. היא מחזירה את מספר קטעי הזמן שנמחקו.

פתח המילוט בטריגר ה-append-only

טבלת האירועים מוגנת בטריגר (deny_mutation) שזורק שגיאה על כל UPDATE או DELETE. תיקון רגיל נעשה ע"י הוספת אירוע תיקון. אבל מחיקה היא לא תיקון: אחרי שהפריט נמחק אין "נושא" שהאירועים מדברים עליו. לכן הטריגר קיבל חריג אחד:

IF current_setting('app.metrics_forget', true) = '1' AND TG_OP IN ('DELETE', 'UPDATE') THEN
  RETURN NULL;
END IF;
RAISE EXCEPTION '% is append-only (attempted %)', ...

המשתנה app.metrics_forget מוגדר רק בתוך הטרנזקציה הנוכחית, ורק לאורך פקודה אחת. TRUNCATE נשאר חסום תמיד.

למה לא פשוט לכבות את הטריגר?ALTER TABLE ... DISABLE TRIGGER לוקח נעילה בלעדית (ACCESS EXCLUSIVE) על כל טבלת האירועים. כל עובד שמנסה לשלוח בדיקה באותו רגע היה נתקע. בנוסף זה דורש הרשאות בעלים על הטבלה, שלאפליקציה אין סיבה להחזיק.

metrics_resync_item_dims(item_id): סנכרון אחרי עריכה

קוראת מחדש את פרטי הפריט מ-items ומעדכנת את העותקים ה"מוקפאים" בריצות, ואחר כך בקטעי הזמן. היא לא מקבלת את הערכים כפרמטרים. היא קוראת אותם בעצמה עם אותם ביטויים שבהם הריצה נוצרה, כך ששני המקומות לא יכולים לצאת מסנכרון. בנוסף, היא מעדכנת רק שורות שבאמת השתנו (IS DISTINCT FROM).

(זמני) metrics_refresh_run_plan

בקומיט הזה נוספה גם פונקציה שמעדכנת את "תוכנית המסלול" של הריצה הפתוחה כשהסוג משתנה, ושינוי סוג אחרי שהפריט יצא משלב 1 נחסם עם 409. שתי ההחלטות האלה בוטלו בשלב 3.

6.3 הצד של TypeScript

src/app/lib/metrics/item-lifecycle.ts (קובץ חדש)

עטיפות דקות שקוראות לפונקציות ה-SQL. החוק החשוב, שכתוב בראש הקובץ: תמיד לקרוא להן עם אותו tx של הכתיבה שלפניהן, כדי שהטבלאות התפעוליות והלדג'ר יתעדכנו יחד או לא יתעדכנו בכלל.

export async function forgetItem(tx: TransactionClient, itemId: bigint): Promise<number> {
  const rows = await tx.$queryRaw<{ n: number }[]>`
    SELECT metrics_forget_item(${itemId}::bigint) AS n`;
  return rows[0]?.n ?? 0;
}

7. שלב 3: שינוי סוג = מסלול חדש abac1a5

7.1 ההחלטה

בשלב 2 שינוי סוג נחסם אחרי שלב 1. הבעיה: זה חוסם את המפעיל במקום לעשות את העבודה. בשלב 3 הוחלט ששינוי סוג = התחלה מחדש. סוג אחר יכול לעבור בתחנות אחרות לגמרי, ולכן הפריט חוזר לשלב 1 של המסלול החדש.

7.2 מה קורה ב-PUT כשהסוג משתנה

הכול בתוך טרנזקציה אחת:

  1. קוראים את הסוג הנוכחי מ-item_routes ומשווים לסוג החדש (typeChanged).
  2. מעדכנים את items כרגיל, כולל הסוג החדש.
  3. מאפסים את item_routes: סוג חדש, מסלול 1, שלב 1, סטטוס 2 (בתור), is_finished = false, והתחנה שמשרתת את שלב 1 של המסלול החדש (findStationForRouteStep).
  4. נוטשים את הריצה הפתוחה בלדג'ר (abandonRun(tx, id, "retyped")).
  5. רושמים מעבר חדש ל-queued (recordTransition). מכיוון שאין ריצה פתוחה, הלדג'ר פותח ריצה חדשה, לפי המסלול של הסוג החדש.
  6. resyncItemDims לשאר השדות.

התשובה כוללת retyped: true כשהיה שינוי סוג.

למה הסדר של שלבים 4 ו-5 חשוב?הלדג'ר משתמש מחדש בריצה פתוחה אם יש כזו, ויש אילוץ (route_run_one_open) שאוסר שתי ריצות פתוחות לאותו פריט. אם לא סוגרים קודם את הישנה, המעבר החדש היה נרשם על הריצה שנבנתה לסוג הישן.

7.3 metrics_abandon_run: לסגור בלי "להשלים"

זה הלב של השלב. בדשבורד יש הגדרה אחת בלבד ל"הושלם": ריצה ש-closed_at שלה מלא. אם סוגרים את הריצה הישנה בדרך הרגילה, הפריט ייספר כאילו נמסר ללקוח רק כי תיקנו לו את הסוג, והוא גם יעוות את ממוצעי זמן הטיפול.

הפתרון: הריצה נסגרת עם is_trusted = false. כל שאילתה בדשבורד שסופרת השלמות כבר מסננת לפי rr.is_trusted, בדיוק למקרים כאלה. כך הריצה נשארת לתיעוד (audit) אבל לא נספרת.

UPDATE route_run
   SET closed_at    = v_at,
       close_reason = p_reason,      -- 'retyped'
       is_trusted   = false
 WHERE route_run_id = v_run;
קטעי הזמן כן נשארים אמיניםהזמן שהפריט בילה בתחנות באמת הושקע, בתחנות אמיתיות, ע"י אנשים אמיתיים. לכן מדדי עומס תחנות ממשיכים לראות אותו. רק "השלמת המסלול" מבוטלת.

פרט עדין בפונקציה: זמן הסגירה (v_at) נקבע למיקרו-שנייה אחת אחרי תחילת קטע הזמן הפתוח האחרון, אם הוא בעתיד. הלדג'ר לפעמים מזיז אירועים קדימה בזמן כדי לשמור על סדר, וסגירה לפי השעון הרגיל הייתה יוצרת טווח זמן ריק או הפוך, שנכשל בבדיקת התקינות (isi_shape).

7.4 הסוג כבר לא מסונכרן לריצות ישנות

metrics_resync_item_dims עודכנה כך שלא תשנה את item_type_id. ההיגיון: לקוח או סיריאלי שגויים הם טעות הקלדה, והערך הישן "אף פעם לא היה נכון", אז מתקנים גם אחורה. הסוג שונה: הריצה הנטושה באמת קרתה תחת הסוג הישן, ושינוי התווית שלה היה מעביר עבודה שנמדדה למסלול שמעולם לא רץ. מאותה סיבה metrics_refresh_run_plan נמחקה: ריצה חדשה היא התשובה הכנה.

7.5 המשלוח הוצא מהעריכה

שדה המשלוח נקבע בקליטה ו"מוקפא" בכל ריצה. העברת פריט ממשלוח למשלוח היא העברה, לא תיקון טעות, והיא צריכה תהליך משלה. לכן:

7.7 איך זה נבדק

לפי הודעת הקומיט, הבדיקות רצו על בסיס הנתונים האמיתי בתוך טרנזקציה שבוטלה בסוף (rollback), כך ששום נתון לא השתנה:

  • פריט באמצע מסלול שונה סוגו: ריצה 12 נסגרה עם retyped ו-is_trusted = false, וריצה חדשה נפתחה על המסלול {1,2}.
  • סך ההשלמות היה 608 לפני ו-608 אחרי, וזו כל המטרה.
  • פריט שכבר הסתיים ושונה סוגו: הריצה המוגמרת שלו נשארת אמינה ונספרת, כי הוא באמת סיים תחת הסוג הישן.
  • ארבע בדיקות התקינות (metrics_selfcheck) נשארו על 0.

8. שלב 4: התאמה למודל המארזים Package model

אחרי הפיצ'ר, מודל המארזים שינה את המבנה: במקום "פריט אבא" ו"פריטים מחוברים" (parent_item_id) יש עכשיו מארז ופריטים בתוכו (package_id). הקוד של עריכה ומחיקה עודכן בהתאם. זה המצב הנוכחי של הקוד:

עריכה (PUT): כללים חדשים

מצבמה קורה
מנסים לשנות סוג של מארזנחסם (409, PACKAGE_TYPE_LOCKED): "לא ניתן לשנות סוג של מארז, יש למחוק וליצור מחדש".
משנים פריט לסוג שהוא בעצמו סוג מארזנחסם (NESTED_PACKAGE): אין מארז בתוך מארז.
פריט בתוך מארז, והמסלול החדש לא מתאים למסלול של המארזנחסם (409, ITEM_ROUTE_SHAPE): המסלול החדש חייב להתחיל ולהיגמר איפה שהמארז מתחיל ונגמר.
פריט בתוך מארז שעדיין בשלב הפתיחהרק הפריט מתחיל מחדש, כמו בשלב 3.
פריט בתוך מארז שכבר נפתחכל המארז חוזר לעמדת הפתיחה (resetPackageToOpening). זה מותר רק עם confirmPackageReset: true, ובלעדיו מתקבל 409 PACKAGE_RESET_REQUIRED.
מארז (לא פריט בתוכו)סיריאלי, דגם ויצרן יכולים להיות ריקים. שדות החובה בשרת: לקוח, סוג ומק"ט.

שגיאות המארזים נזרקות כ-PackageError עם code ו-status, והשרת מחזיר אותם כ-JSON: { error, code }. גם workerId ו-workerName נשלחים עכשיו, כדי שאירועי הלדג'ר יירשמו על שם העובד.

מחיקה (DELETE): כללים חדשים

  • מחיקת מארז מוחקת את כל הפריטים שבתוכו. בלי cascade: true מתקבל 409 PACKAGE_HAS_ITEMS עם הרשימה, בדיוק כמו המנגנון מהשלב הראשון.
  • מחיקת הפריט האחרון במארז נחסמת (409 LAST_PACKAGE_ITEM), כי אסור מארז ריק. צריך למחוק את המארז עצמו.
  • אחרי שפריט יוצא ממארז, נבדק מחדש אם המארז מוכן לסגירה (recheckPackageReadiness), כי אולי זה היה הפריט האחרון שחיכו לו.

בצד הממשק השינוי קטן: ב-EditItemDialog.tsx "תת-פריט" מזוהה עכשיו לפי item.package_id במקום parent_item_id.

  1. UI "מחק לצמיתות", ונשלח DELETE בלי גוף.
  2. API נמצאו פריטים בתוך המארז, ולכן נשלח 409 עם connectedItems.
  3. UI החלון מציג את רשימת הפריטים (מספר, דגם, סיריאלי) ואת הכפתור "מחק את הפריט והפריטים המחוברים".
  4. UI אישור, ונשלח DELETE עם { cascade: true }.
  5. DB "לשכוח" את כולם בלדג'ר, למחוק שורות תפעוליות, קודם הפריטים שבפנים (הם מחזיקים את ה-FK) ואז המארז.

11. שאלות נפוצות

למה אי אפשר לערוך סטטוס או התקדמות מהחלון?

הם שייכים ל-item_routes ומונעים ע"י תהליך הבדיקה בתחנות. שינוי ידני היה עוקף את הלדג'ר ויוצר מצב שלא קרה באמת. החריג היחיד הוא שינוי סוג, שמאפס את המסלול בצורה מבוקרת.

למה כל דבר בטרנזקציה אחת?

כי יש כמה טבלאות שחייבות להסכים זו עם זו. אם, למשל, המחיקה מ-items הייתה מצליחה והניקוי של הלדג'ר נכשל, היינו חוזרים בדיוק לבאג של "פריט רוח רפאים". בטרנזקציה, או שהכול קורה או ששום דבר לא קורה.

למה פונקציות SQL ולא קוד TypeScript?

הכללים של הלדג'ר (append-only, ריצה פתוחה אחת, סדר מחיקה לפי FK, נעילות) כבר חיים בבסיס הנתונים. כשהלוגיקה נמצאת שם, היא משתמשת באותם ביטויים ובאותן נעילות כמו שאר הלדג'ר, ואי אפשר "לשכוח" אותה אם מישהו כותב נתיב אחר לבסיס הנתונים.

אם שיניתי סוג בטעות, איך מחזירים?

משנים שוב לסוג המקורי, אבל הפריט יתחיל שוב משלב 1. ההתקדמות הקודמת לא חוזרת, ולכן יש אזהרה לפני השמירה. ההיסטוריה ותוצאות הבדיקה הקודמות כן נשמרות.

למה אי אפשר לשנות משלוח?

המשלוח "מוקפא" בכל ריצה בלדג'ר ומשפיע על דוחות לפי משלוח. העברה בין משלוחים היא פעולה עסקית נפרדת (העברה) ולא תיקון טעות, ולכן צריכה תהליך משלה, שעוד לא נבנה.

מה ההבדל בין "נטישה" של ריצה למחיקה שלה?

מחיקה (forget) מעלימה את הריצה לגמרי, וזה מתאים רק כשהפריט עצמו נמחק. נטישה (abandon) סוגרת אותה ומסמנת אותה כלא-אמינה: היא נשארת לתיעוד, הזמן שנמדד בתחנות ממשיך להיספר בעומס, אבל היא לא נספרת כהשלמה.
