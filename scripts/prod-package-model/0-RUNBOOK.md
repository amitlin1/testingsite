# שדרוג הייצור למודל המארזים — מה מריצים, לפי הסדר

התיקייה הזו היא החבילה. מעתיקים אותה לשרת ומריצים לפי הסדר שלמטה.

**מצב הפתיחה:** הייצור **אחרי** שדרוג המטריקות (הדשבורד/לדג'ר) ו**לפני** מודל
המארזים. כך מוודאים שזה באמת המצב — שתי שורות, לפני שנוגעים במשהו:

```sql
SELECT version FROM metrics_schema_version WHERE id = 1;   -- צריך להחזיר 2
SELECT to_regclass('public.package_contents');             -- צריך להחזיר NULL
```

אם הראשונה כבר מחזירה 3 — השדרוג הזה כבר רץ. עצור.

**הקובץ המאוחד נושא שתי מיגרציות**, לא אחת: `20260915120000_package_model`
(מודל המארזים) ו-`20261006120000_package_contents_drop_manufacturer_sku`
(ביטול עמודת ה-SKU מהתבנית — אשף הפתיחה מוצא פריט ייחוס לפי מה שנסרק). שתיהן
מוחלות ונרשמות באותה ריצה, כך ש-`migrate deploy` של הגרסה החדשה לא מוצא מה
להריץ. הסקריפט `prod-deploy/db-server/scripts/10-apply-package-sku-drop.ps1`
**לא נחוץ כאן** — הוא נועד ל-DB ששודרג למארזים *לפני* שהעמודה בוטלה.

**הסדר: קודם ה-DB, אחר כך האפליקציה.** ה-image החדש דורש גרסת סכימה 3
(`REQUIRED_METRICS_SCHEMA_VERSION` ב-`src/app/lib/metrics/schema-gate.ts`), ומול
DB בגרסה 2 הוא מסרב לכתוב ומחזיר 503 מסודר. זאת רשת ביטחון, לא תוכנית.

## שלב 0 — אבחון (קריאה בלבד)

הרץ את `scripts/diagnose-legacy-for-packages.sql` על ייצור ושמור את הפלט.

**זה לא טקס.** הקובץ המאוחד רץ ב-`cfg_strict = true`: **קבוצה חסומה אחת מבטלת
את כל השדרוג.** קבוצה חסומה = פריט ישן שכבר עבדו עליו (תוצאות, היסטוריית
עמדות, מחקר או קבצים — תלוי ב-CONFIG). האבחון האחרון נעשה ב-17.09.2026 ומצא
110 פריטי KVM במשלוח אחד, אף אחד לא נבדק — הכול ניתן להסבה. **עברו מאז שלושה
שבועות.** כל פריט שנבדק בינתיים הופך לחסום, והשדרוג יסרב. לכן: אבחון טרי,
באותו יום.

## שלב 1 — גיבוי

על שרת ה-DB, PowerShell:

```powershell
.\1-backup-before-packages.ps1
.\1-backup-before-packages.ps1 -OutDir "D:\backups"     # יעד אחר
```

הסקריפט לוקח `pg_dump -Fc` מתוך הקונטיינר, מוציא את הקובץ החוצה, **ומשחזר אותו
ל-DB זמני ומשווה ספירות** — כך יודעים שאפשר באמת לחזור אחורה. בסוף הוא מדפיס
את פקודת השחזור; שמור אותה. בלי השורה הירוקה "השחזור הצליח ותואם למקור" —
לא ממשיכים.

> עצור את האפליקציה לפני הגיבוי (`docker compose stop next-app` על שרת
> האפליקציה). שורה שנכתבת בין הגיבוי להרצה אובדת בשחזור.

## שלב 2 — לוודא את ה-CONFIG

בראש `2-upgrade-to-packages.sql` (שורות ~41–61) יושב בלוק CONFIG. הערכים הנוכחיים
נגזרו מהאבחון של 17.09:

| הגדרה | ערך נוכחי |
|---|---|
| `cfg_opening_type` / `cfg_closing_type` | `צילום` / `אריזה` |
| `cfg_remove_from_item_routes` | `דוח סופי` |
| `cfg_packages` | מארז מחשב (מחשב+עכבר+מקלדת), מארז KVM 4 PORTS, מארז KVM 8 PORTS |
| `cfg_legacy_map` | `KVM 4 PORTS → מארז KVM 4 PORTS`, `KVM 8 PORTS → מארז KVM 8 PORTS` |
| `cfg_research_policy` / `cfg_files_policy` | `reset` / `move` |
| `cfg_strict` | `true` (נכפה בבנייה) |

שמות העמדות וסוגי הפריט חייבים להתקיים בייצור **בדיוק כך** — אחרת הסקריפט עוצר
עם `CONFIG: סוג עמדת הפתיחה "..." לא קיים`. בדוק מול:

```sql
SELECT test_type_desc FROM test_stations_type ORDER BY 1;
SELECT item_type_desc FROM item_types ORDER BY 1;
```

צריך לשנות? ערוך את `03-fix-production.sql` והרץ `node build-upgrade.mjs`,
שבונה מחדש את `2-upgrade-to-packages.sql`. אל תערוך את הקובץ המאוחד ישירות.

## שלב 3 — השדרוג

DBeaver, מחובר **באותו משתמש שאיתו הותקן הקונטיינר** (`POSTGRES_USER`): פתח את
`2-upgrade-to-packages.sql` ולחץ **Alt+X** (Execute script) — לא Ctrl+Enter.

```
psql -U <user> -d <db> -v ON_ERROR_STOP=1 -f 2-upgrade-to-packages.sql
```

הכול בפעולה אחת: בדיקות מקדימות → המיגרציה → רישום ב-`_prisma_migrations` →
סידור הנתונים → הסבת הפריטים הישנים. **הכול או כלום.** בסוף שתי לשוניות:
הדוח, ומיפוי המזהים ישן→חדש.

הרצה חוזרת מסרבת ("הסכימה כבר שודרגה") — זה תקין, לא תקלה.

### אם השדרוג סירב

**`cfg_strict: N קבוצות חסומות — לא נשמר כלום`** — יש פריטים ישנים שעבדו עליהם.
שום דבר לא נשמר. שלוש אפשרויות, לפי סדר העדפה:

1. **לסיים אותם בממשק הישן** לפני השדרוג (הכי נקי), ואז להריץ שוב.
2. **להסב רק את מה שאפשר**: להריץ `02-migrate-production.sql` ואז
   `03-fix-production.sql` (שם `cfg_strict = false`). `03` מסתיים ב-`ROLLBACK;`
   — הרצה יבשה שמדפיסה דוח בלי לשמור. כשהדוח נראה נכון, להחליף ל-`COMMIT;`
   ולהריץ שוב. החסומות יישארו במבנה הישן ויופיעו כ"קבוצות ישנות שלא הוסבו"
   באימות — החלטה מודעת, לא תקלה.
3. **למחוק ולהזין מחדש** דרך טופס הקליטה החדש, אם הכמות קטנה.

שגיאה אחרת — התיקון בהודעה עצמה. אחרי תיקון אפשר להריץ שוב; אם DBeaver נשאר
בטרנזקציה פתוחה, הרץ `ROLLBACK;`.

## שלב 5 — לשמור את מיפוי המזהים

כל פריט שהוסב קיבל מזהה חדש בן 16 ספרות — **המדבקות הישנות כבר לא תקפות.**

```sql
SELECT package_id, package_seq, new_id, legacy_id, item_type, serial_no, shipment_code
  FROM legacy_id_map ORDER BY package_id, package_seq;
```

ייצא ל-CSV (DBeaver: Export → CSV) ושמור. זה המקור להדפסת המדבקות החדשות.

## שלב 6 — האפליקציה

במכונת הפיתוח:

```powershell
docker build -t testingsite-next-app:latest .
docker save -o next-app.tar testingsite-next-app:latest
```

העבר את הקובץ לשרת האפליקציה, ושם, מתוך `prod-deploy/app-server`:

```powershell
docker load -i next-app.tar
docker compose up -d next-app
docker restart nginx          # nginx פותר את next-app בעלייה
```

בדיקות:

| בדיקה | ציפייה |
|---|---|
| `http://<APP-IP>/api/health/schema` | `{"version":3}` |
| קליטת מארז חדש מהממשק | נוצר מזהה בן 16 ספרות שמסתיים ב-00 |
| אשף פתיחת מארז על מארז בתור | עובר, כל פריט מקבל תוצאה |
| הדשבורד | נטען, מספרים סבירים |
| עובד שאינו מנהל פותח משלוח | שדה "עובד מקבל" מתמלא בשמו |

> מהשינוי של ההרשאות לפי תפקיד: לכל משתמש **שאינו מנהל** חייב להיות מספר עובד
> ב-Keycloak, אחרת שדות העובד במשלוחים נחסמים עם "לא ניתן לזהות אותך". נבדק
> בהגדרות ← משתמשים.

אין משימות מתוזמנות חדשות בשדרוג הזה — מה שנרשם בשדרוג המטריקות ממשיך לרוץ.

## חזרה אחורה

עד שלב 3 כולל: אין מה להחזיר — אם השדרוג נכשל הוא לא שמר כלום.

אחרי שהשדרוג נשמר, החזרה היא **שחזור הגיבוי בלבד** (ואיתו אובד כל מה שנכתב
מאז):

```powershell
docker cp "<קובץ הגיבוי>" postgres:/tmp/restore.dump
docker exec postgres pg_restore -U <user> -d <db> --clean --if-exists --no-owner /tmp/restore.dump
docker exec postgres rm -f /tmp/restore.dump
```

ואז להחזיר את ה-image הקודם של האפליקציה (`docker compose up -d next-app` עם
התג הישן). image ישן מול DB משודרג יעבוד חלקית — אל תשאיר את זה ככה.

- **הקובץ המאוחד מסונכרן** עם מקורותיו: הרצתי `build-upgrade.mjs` מחדש, אפס
  הבדלים — גם אחרי שנוספה אליו המיגרציה השנייה (`FOLLOW_UPS` בבונה).

  - עם `cfg_strict = true` ו-520 קבוצות שעבדו עליהן — סירב, **ולא השאיר כלום**:
    אחרי הסירוב `package_contents` לא קיימת ו-`_prisma_migrations` נקי.
    האטומיות עובדת.
  - עם `cfg_strict = false` — רץ מקצה לקצה, הדפיס דוח ומיפוי מזהים, והסב את
    הקבוצות שלא היו חסומות למזהים החדשים.
  - ה-DB הזמני נמחק אחרי הבדיקה.
- **`3-verify-after-upgrade.sql` נבדק** על DB משודרג אמיתי (`testingsite_pkgtest`):
  כל הבדיקות OK, והבדיקה "קבוצות ישנות שלא הוסבו" תפסה נכון 112 קבוצות ב-DB
  שרצה בו רק הסכימה בלי סידור הנתונים.

**מה לא נבדק:** ה-CONFIG עצמו מול נתוני הייצור. אין כאן עותק של DB הייצור —
השיבוט שבדקתי הוא ה-DB של הפיתוח, עם עמדות וסוגי פריט אחרים (לבדיקה הרצתי
אותו עם CONFIG מותאם לפיתוח). האימות של ה-CONFIG האמיתי הוא האבחון של שלב 0,
והוא חייב להיעשות על הייצור ביום ההרצה.
